# 本地桌宠 MVP 设计

日期：2026-08-02

状态：待用户审阅

## 背景

本项目目标是做一个跨平台桌宠程序。长期方向可以扩展为情侣/好友桌宠，包括定向绑定、串门互动、消息和语音互动。第一阶段只做本地桌宠底座，不引入账号、联网、匹配、语音或 AI agent。

产品路线采用自主研发主工程，参考成熟开源项目的设计经验，不直接 fork 大型桌宠项目，不复制授权不明确的代码、素材、模型或音频。

## 已确认决策

- 技术栈：Tauri 2 + React + TypeScript + PixiJS。
- 角色表现：第一版使用 2D 序列帧。
- 养成系统：第一版不做心情、体力、亲密度、投喂、任务或道具。
- 跨平台策略：Windows 优先验收，macOS/Linux 保持可运行设计。
- 发布策略：第一版只要求开发环境可运行，不做安装包和自动更新。
- 桌宠行为：支持待机、拖拽、点击反馈、气泡和简单自动移动。
- 资源策略：第一版使用参考图风格的内置示例角色和固定动作配置，不做资源包导入管理器。
- 动作帧来源：由项目使用 imagegen/gpt-image-2 工作流基于用户提供的参考图生成，不要求用户手工提供完整动作帧。
- 设置策略：提供轻量设置面板。

## 非目标

第一版不实现以下能力：

- 公共随机匹配。
- 远程控制对方电脑。
- 账号系统。
- 消息聊天。
- 语音通话。
- AI 对话或主动 agent。
- Live2D。
- 用户导入资源包。
- 商店、创意工坊、支付。
- 安装包、签名、自动更新。

这些能力后续作为独立 spec 设计，不能挤入本地桌宠 MVP。

## 参考原则

- 参考 BongoCat Next 的 Tauri 透明窗口、置顶、点击穿透和 Live2D 扩展方向。
- 参考 OpenPets 的模块边界和扩展能力设计。
- 参考 VPet 的动作状态机和桌宠玩法组织方式。
- GPL/AGPL 项目只能作为设计参考，不复制代码。
- 示例素材必须自制或使用授权明确的资源。

## 角色美术方向

第一版内置角色基于用户提供的参考图重新设计，不直接复制原图像素。角色方向是“星星睡衣小星人”：

- 黄色星形睡衣或星星帽轮廓。
- 橙色圆脸。
- 大眼睛，眼睛内有星星高光。
- 红色圆脸颊。
- 小而温和的微笑。
- 帽尖或头顶带小星星装饰。
- 整体保留手绘、蜡笔、儿童插画质感。
- 动作帧不强依赖衣服上的文字；如果文字影响小尺寸清晰度，使用星星图案或短划线装饰替代。

动作帧生成要求：

- 参考图作为风格和角色设定参考，不作为逐像素编辑目标。
- 使用 imagegen/gpt-image-2 生成项目内置动作帧。
- 生成时使用纯色 chroma-key 背景，再本地移除背景得到透明 PNG。
- 每帧保持角色比例、主色、脸部特征和线条质感一致。
- 最终资源存入项目目录，不能只保留在临时目录或生成工具默认目录。
- 如果当前环境无法使用 imagegen/gpt-image-2，不能改用版权不明的网上素材；必须明确说明限制并等待处理。

## 用户体验

第一版打开后展示一个透明无边框桌宠窗口。桌宠默认置顶，显示在桌面上，不遮挡大片工作区域。用户可以拖拽桌宠，右键打开菜单，也可以通过设置面板调整缩放、自动移动和气泡行为。

桌宠会在空闲时播放待机动画，并在设定范围内进行简单自动移动。点击桌宠会触发短暂的反馈动作和气泡。用户拖拽时桌宠进入拖拽状态，松开后保存位置并回到待机或行走状态。

用户可以随时通过托盘菜单隐藏、显示、打开设置或退出程序。点击穿透需要显式开关，避免桌宠影响正常工作。

## 架构

项目采用前端渲染层与桌面系统能力分离的结构。

推荐目录：

```text
src/
  app/
    App.tsx
    routes.ts
  desktop/
    desktopApi.ts
    windowCommands.ts
  pet-core/
    petStateMachine.ts
    petScheduler.ts
    petTypes.ts
  renderer/
    PixiPetStage.tsx
    animationPlayer.ts
    frameAtlas.ts
  bubble/
    BubbleLayer.tsx
    bubbleStore.ts
  settings/
    settingsStore.ts
    defaultSettings.ts
    SettingsPanel.tsx
  assets/
    builtInPetManifest.ts
    pets/
src-tauri/
  src/
    main.rs
    commands.rs
```

模块职责：

- `desktop`：封装 Tauri 命令调用，不让 UI 组件直接依赖窗口 API。
- `pet-core`：纯 TypeScript 状态机和调度逻辑，不依赖 React 或 PixiJS。
- `renderer`：使用 PixiJS 播放当前动作帧。
- `bubble`：显示点击反馈、提示和状态气泡。
- `settings`：管理设置默认值、持久化和设置面板。
- `assets`：保存第一版内置资源清单和动作配置。
- `src-tauri`：提供透明窗口、置顶、点击穿透、托盘、窗口位置和退出等系统能力。

## 数据流

用户输入、计时器和设置变化通过事件进入应用：

1. 鼠标点击、拖拽或自动调度事件进入 `pet-core`。
2. `pet-core` 根据当前状态和事件计算下一个状态。
3. `renderer` 根据状态读取动作配置并播放对应帧。
4. `bubble` 根据状态或交互事件显示短气泡。
5. `settings` 变化写入本地存储，并通过 `desktop` 调整窗口行为。
6. Tauri/Rust 只负责系统能力，不保存业务状态。

本地 MVP 不建立 `sync` 模块。后续联网互动需要通过新模块订阅 `pet-core` 的事件，而不是改写状态机内部。

## 状态机

第一版状态：

- `idle`：待机。
- `walking`：简单自动移动。
- `dragging`：用户拖拽中。
- `happy`：点击反馈。
- `sleeping`：长时间无交互后的低频状态。

核心事件：

- `APP_READY`：应用启动完成。
- `PET_CLICKED`：用户点击桌宠。
- `DRAG_STARTED`：开始拖拽。
- `DRAG_ENDED`：结束拖拽。
- `AUTO_MOVE_TICK`：自动移动调度。
- `IDLE_TIMEOUT`：长时间无交互。
- `SETTINGS_CHANGED`：设置变化。

状态机规则：

- `dragging` 优先级最高，拖拽中不触发自动移动。
- `happy` 是短暂状态，动画结束后回到 `idle`。
- `walking` 只在自动移动启用时出现。
- `sleeping` 可以被点击、拖拽或设置变化唤醒。
- 所有状态转换要可测试，不能散落在 React 组件中。

## 动画和资源

第一版使用内置示例角色，动作配置写在 TypeScript manifest 中。每个动作包含帧列表、帧率、循环方式、默认尺寸和锚点。

示例动作：

- `idle`：4 帧循环，轻微呼吸和星星帽摆动。
- `walk`：6 帧循环，左右轻摆或小步移动。
- `drag`：2 帧循环或单帧，身体被拎起或轻微倾斜。
- `happy`：4 帧播放一次，脸颊更红、眼睛高光更明显。
- `sleep`：4 帧低帧率循环，闭眼或半闭眼，帽尖小星星轻微晃动。

第一版不做资源包导入，但 manifest 结构要接近未来 `pet.json`，方便后续迁移。

## 桌面能力

第一版需要支持：

- 透明无边框窗口。
- 始终置顶开关。
- 窗口拖拽。
- 点击穿透开关。
- 托盘菜单：显示、隐藏、设置、退出。
- 保存和恢复窗口位置。
- 读取主屏幕尺寸，用于限制自动移动范围。

Windows 是主要验收平台。macOS/Linux 的系统差异要通过封装层隔离，无法支持的能力要降级为无害行为，并在设置或日志中可见。

## 设置面板

轻量设置面板包含：

- 桌宠缩放。
- 自动移动开关。
- 自动移动范围。
- 气泡开关。
- 始终置顶开关。
- 点击穿透开关。
- 重置位置。

设置保存到本地。第一版使用应用数据目录下的轻量 JSON 文件，通过 Tauri 命令读写，避免为了少量设置提前引入额外存储插件。

## 错误处理

- 资源加载失败时显示内置占位动作，不让应用白屏。
- 设置读取失败时回退默认设置，并保留错误日志。
- 窗口命令失败时不崩溃，设置状态回滚到实际状态。
- 自动移动边界异常时回退到屏幕安全区域。
- PixiJS 初始化失败时显示简单 React 文本占位，方便开发定位。

## 测试和验证

第一版至少验证：

- TypeScript 类型检查通过。
- 前端构建通过。
- Rust/Tauri 检查或开发运行通过。
- `pet-core` 状态机有单元测试，覆盖点击、拖拽、自动移动和睡眠唤醒。
- 设置默认值和持久化读写有基础测试。
- Windows 上手工验证透明窗口、置顶、拖拽、托盘、点击穿透和退出。

如果 macOS/Linux 无法在当前机器实测，至少保证平台相关代码集中在 `desktop` 和 `src-tauri` 封装中，并记录未实测风险。

## 开发协作

主代理负责维护本 spec、拆分任务、约束范围和代码审核。固定后台开发任务负责主要编码实现、测试补充和构建修复。

每次分发编码任务时，主代理需要提供：

- 目标。
- 涉及模块。
- 不允许改动的范围。
- 预期验证命令。
- 交付格式。

后台开发任务完成后，主代理进行代码审核。审核重点是跨平台边界、授权风险、模块职责、状态机可测试性、UI 是否过度复杂和验证结果是否可信。

## 验收标准

第一版完成时应满足：

- 运行开发命令后出现透明桌宠窗口。
- 桌宠能播放内置 2D 序列帧动画。
- 桌宠支持拖拽，释放后位置被保存。
- 点击桌宠会展示反馈动作和气泡。
- 桌宠能在配置范围内简单自动移动。
- 托盘菜单可以显示、隐藏、打开设置和退出。
- 设置面板可以调整缩放、自动移动、气泡、置顶、点击穿透，并能持久化。
- 状态机和设置核心逻辑有自动化测试。
- 不包含联网、账号、AI、语音、资源包导入或打包发布能力。

## 风险和取舍

- Tauri 的透明窗口、点击穿透和托盘能力在不同平台存在差异，第一版只承诺 Windows 优先验收。
- PixiJS 渲染足够支持 2D 序列帧，但 Live2D 需要后续单独设计。
- 固定内置资源能降低第一版复杂度，但后续资源包导入需要补格式校验和错误提示。
- 不做安装包会降低第一版交付复杂度，但用户试用前仍需要开发环境。
- 不做养成系统能保持底座清晰，但第一版玩法会偏基础。

## 后续 spec

本地桌宠 MVP 完成后，再按顺序规划：

1. 资源包导入和角色切换。
2. Live2D 支持。
3. 本地轻量养成。
4. 情侣/好友定向绑定。
5. 桌宠串门和动作同步。
6. 消息和语音互动。
