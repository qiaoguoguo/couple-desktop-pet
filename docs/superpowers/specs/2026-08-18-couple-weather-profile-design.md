# 双方天气与基本资料同步设计

日期：2026-08-18  
状态：已批准

## 目标

为情侣桌宠增加“双方天气”功能：用户在设置中手动选择昵称和所在城市，服务端持久化双方基本资料并在绑定时同步；点击互动菜单中的“双方天气”后，以已确认的情侣化界面展示双方当前天气、当前温度、今日最高/最低温和降雨概率。

该功能应保持轻量：不读取系统定位，不后台轮询天气，不引入付费天气成本，也不把天气数据混入桌宠动作状态机。

## 已确认的产品决策

- 用“双方天气”替换六宫格中的“撒娇卖萌”，保留“求抱抱”。
- 基本资料仅包含昵称和城市级位置。
- 城市由用户搜索并从标准结果中选择，不接受未解析的自由文本。
- 服务端持久化基本资料；首次绑定、重连和绑定后修改资料时同步给对方。
- 使用 WeatherAPI.com 免费套餐；允许注册免费 API Key，但不接受任何付费兜底或自动升级。
- WeatherAPI Key 只存在于 Relay 服务端环境变量，不进入桌面客户端、安装包或仓库。
- 每次点击“双方天气”都会请求 Relay；Relay 对每个城市使用 1 小时缓存，命中则返回，过期则重新查询供应商。
- 供应商查询失败时，可降级到 6 小时内的旧缓存，并明确标记数据没有更新。
- 天气面板沿用现有外卖发送框的黑、白、红视觉语言，并以已确认的浏览器设计稿为视觉基准。

## 范围边界

### 本期包含

- 本地基本资料设置和持久化。
- 服务端设备资料和城市资料持久化。
- 城市搜索代理和结果选择。
- 绑定时的双方资料同步。
- 已绑定后的资料更新和实时通知。
- 双方天气查询、缓存、过期刷新和旧缓存降级。
- 双方天气面板及未绑定、资料缺失、加载、部分失败和完全失败状态。
- 情侣化关怀文案规则。
- 新互动菜单天气图标资源。
- Relay 部署配置和免费 API Key 说明。

### 本期不包含

- GPS、IP 定位或操作系统位置权限。
- 详细地址、区县以下位置或位置轨迹。
- 多日天气预报、小时预报、空气质量、预警和生活指数。
- 天气变化通知、后台定时刷新或开机自动请求。
- AI 生成天气文案。
- 天气历史、城市收藏或任意城市查询工具。
- 付费天气供应商、自动充值或付费接口回退。
- 新桌宠动作或天气对应的角色动画。

## 用户流程

### 首次设置与绑定

1. 用户打开设置中的“基本信息”。
2. 输入昵称，点击城市搜索按钮或按回车进行搜索。
3. 从最多 5 个结果中选择一个标准城市。
4. 保存资料；客户端先保存本地资料，再请求 Relay 持久化。
5. 用户创建绑定码或接受绑定码时，新客户端随请求提交当前资料。
6. 绑定完成响应返回对方资料；双方将对方资料保存到本地缓存。
7. WebSocket 鉴权成功后，Relay 再发送当前对方资料，修正任何旧缓存。

资料不完整时不能创建或接受绑定。界面应先引导完成昵称和城市设置。

### 绑定后修改资料

1. 用户修改昵称或城市并保存。
2. Relay 校验设备凭据并原子更新设备昵称和城市记录。
3. Relay 向在线的绑定对象推送 `peer.profile`。
4. 对方客户端更新本地对方资料缓存。
5. 对方离线时不需要排队事件；下次 WebSocket 鉴权会返回最新资料。

### 查看双方天气

1. 用户点击“双方天气”。
2. 客户端立即打开固定尺寸加载面板，并向 Relay 请求当前绑定双方的天气。
3. Relay 从数据库读取双方城市，客户端不能提交任意查询坐标。
4. Relay 对每个城市独立检查 1 小时缓存。
5. 未过期的数据直接返回；过期或缺失的数据并发请求 WeatherAPI。
6. 客户端独立渲染双方结果，一方失败不遮蔽另一方。
7. 关闭并再次打开面板会再次请求 Relay，但不会绕过 Relay 缓存。

## 基本资料数据模型

共享协议增加稳定、可序列化的资料类型：

```ts
interface CityLocationV1 {
  provider: "weatherapi";
  providerLocationId: number;
  name: string;
  region: string;
  country: string;
  latitude: number;
  longitude: number;
}

interface DeviceProfileV1 {
  version: 1;
  nickname: string;
  city: CityLocationV1 | null;
  updatedAt: string;
}

interface ProfileUpdateV1 {
  version: 1;
  nickname: string;
  city: CityLocationV1;
}
```

校验规则：

- `nickname` 去除首尾空白后为 1 至 20 个 Unicode 字符。
- 城市名称、地区和国家字段分别限制为 80 个 Unicode 字符。
- 纬度必须在 `-90..90`，经度必须在 `-180..180`。
- `providerLocationId` 必须为正整数。
- 官方客户端只允许保存城市搜索结果，不提供经纬度编辑入口。
- 服务端校验所有城市字段、坐标范围和更新频率；天气接口只读取已认证设备自己的资料，不能提交临时坐标。
- 旧客户端或旧数据可暂时表现为 `city: null`，但新客户端保存和绑定时必须选择城市。

## 数据库设计

保留现有 `devices.display_name`，将其作为昵称的唯一服务端来源。新增表：

```sql
CREATE TABLE IF NOT EXISTS device_locations (
  device_id TEXT PRIMARY KEY,
  provider TEXT NOT NULL,
  provider_location_id INTEGER NOT NULL,
  city_name TEXT NOT NULL,
  region_name TEXT NOT NULL,
  country_name TEXT NOT NULL,
  latitude REAL NOT NULL,
  longitude REAL NOT NULL,
  updated_at TEXT NOT NULL,
  FOREIGN KEY (device_id) REFERENCES devices(device_id)
);
```

迁移必须是可重复执行的增量迁移，不重建或清空现有 `devices`、`pairs` 和 `pair_codes`。读取资料时将 `devices.display_name` 与 `device_locations` 合并为 `DeviceProfileV1`。

## HTTP 接口

### 城市搜索

`POST /locations/search`

请求只包含设备凭据和查询词。查询词去除首尾空白后为 2 至 80 个字符。Relay 使用 WeatherAPI `/search.json`，最多返回 5 个规范化城市结果。

行为约束：

- 未注册设备可以通过该请求建立只有身份凭据的设备记录，但不能提前写入或修改 `display_name`。
- 相同规范化查询结果缓存 24 小时。
- 每个设备和来源 IP 最多 10 次搜索/分钟。
- 不向客户端返回 WeatherAPI Key 或供应商原始响应。
- 城市搜索失败时保留当前已选择城市，不清空表单。

### 保存资料

`PUT /devices/profile`

请求包含设备凭据和 `ProfileUpdateV1`。服务端使用自己的时钟生成 `updatedAt`，并在同一事务中写入昵称和城市。

每个设备最多保存 10 次资料/小时，防止通过频繁更换坐标消耗免费天气额度。

成功响应返回服务端规范化后的完整资料。保存成功后，若设备已绑定且对方在线，Relay 推送 `peer.profile`。

### 创建和接受绑定

现有 `CreatePairCodeRequest` 与 `AcceptPairCodeRequest` 增加可选的 `profile` 字段以保持旧客户端兼容。新客户端始终提交完整资料。

- `AcceptPairCodeResponse` 增加 `peerProfile`。
- `PairCodeStatusResponse` 的 `paired` 分支增加 `peerProfile`。
- 旧客户端没有城市时仍可被服务端识别，但新客户端会在本地阻止资料不完整的绑定操作。

### 查询双方天气

`POST /pairs/weather`

请求只包含设备凭据和 `pairId`。Relay 必须验证设备属于活动绑定，并从数据库读取双方城市；不接受客户端提供城市或坐标。

响应按 `self` 和 `peer` 返回两个独立条目：

```ts
type WeatherConditionV1 =
  | "clear"
  | "partly-cloudy"
  | "cloudy"
  | "fog"
  | "rain"
  | "snow"
  | "thunder"
  | "other";

interface WeatherSnapshotV1 {
  version: 1;
  condition: WeatherConditionV1;
  conditionText: string;
  currentTemperatureC: number;
  maxTemperatureC: number;
  minTemperatureC: number;
  rainChancePercent: number;
  fetchedAt: string;
  source: "live" | "cache" | "stale-cache";
}
```

每个条目同时携带对应 `DeviceProfileV1`，并且只能是以下两种状态之一：

- `{ status: "ready", profile, weather }`
- `{ status: "unavailable", profile, reason }`

`reason` 只使用稳定枚举，例如 `profile_incomplete`、`provider_unavailable`、`quota_exhausted`，不把供应商内部错误文本直接暴露给用户。

## WebSocket 协议

新增资料同步能力标识和服务端事件：

```ts
const PROFILE_SYNC_CAPABILITY = "profile-v1";

interface PeerProfileServerMessage {
  type: "peer.profile";
  pairId: string;
  peerDeviceId: string;
  profile: DeviceProfileV1;
  changedAt: string;
}
```

- 新客户端在 `auth` 中声明 `profile-v1`。
- Relay 在 `auth.ok` 后向支持该能力的客户端发送当前 `peer.profile`。
- HTTP 资料更新成功后，Relay 向在线且支持该能力的对方推送相同事件。
- 不要求旧 Relay 或旧客户端理解该事件；解析器必须忽略未知能力和未知事件，不中断现有消息、状态和外卖通信。

## WeatherAPI 适配

Relay 增加独立 `WeatherProvider` 边界，第一版只有 WeatherAPI 实现。业务层不能依赖供应商原始 JSON。

供应商调用：

- 城市搜索：`/v1/search.json`
- 当天天气：`/v1/forecast.json?days=1&aqi=no&alerts=no&lang=zh`
- 使用 HTTPS。
- API Key 从 `WEATHER_API_KEY` 读取。
- 请求设置明确超时，并对响应字段进行运行时校验。
- 供应商图标 URL 不进入客户端；使用 `condition.code` 映射本地天气类别和本地图标。

免费成本边界：

- 在 2026-08-18 的设计确认时，WeatherAPI 官方价格页列出的免费套餐为每月 100,000 次调用、价格为 0，并允许商业使用；正式发布前仍需重新核对供应商条款。
- 部署使用 WeatherAPI 免费账号，不配置支付凭据或付费套餐。
- 应用没有自动升级、自动充值或其他天气供应商付费回退逻辑。
- 免费额度耗尽时返回 `quota_exhausted`，有旧缓存则按旧缓存规则降级，否则显示不可用。
- UI 页脚显示 `WeatherAPI.com` 署名。

## 缓存与并发

### 天气缓存

- 缓存键使用规范化后的 `latitude.toFixed(4)` 与 `longitude.toFixed(4)`。
- 新鲜 TTL 为 1 小时，从成功供应商请求的 `fetchedAt` 计算。
- 每次打开面板仍会请求 Relay；只有 Relay 决定是否命中缓存。
- 缓存过期时必须尝试重新查询供应商。
- 查询失败后，若旧数据距离 `fetchedAt` 不超过 6 小时，返回 `stale-cache`。
- 超过 6 小时的旧数据不得展示为天气结果。
- 同一缓存键的并发过期请求必须合并为一个供应商请求，避免缓存击穿。
- 双方城市分别缓存和查询；同城情侣共享同一缓存条目。

### 城市搜索缓存

- 规范化查询词为去除首尾空白并统一大小写后的字符串。
- 搜索结果缓存 24 小时。
- 搜索缓存与天气缓存分离，不共享 TTL 或错误状态。

第一版缓存为 Relay 进程内存缓存，不写入 SQLite。服务重启后缓存为空是可接受行为；基本资料仍必须持久化。

## 客户端状态与持久化

在设置边界中新增独立资料状态，不把资料字段塞进窗口或桌宠动作状态：

```ts
interface ProfileSettings {
  local: EditableProfileV1;
  peerByDeviceId: Record<string, DeviceProfileV1>;
  syncState: "idle" | "saving" | "synced" | "pending" | "error";
}
```

- 本地资料保存到现有设置存储。
- 对方资料按 `peerDeviceId` 缓存，解绑后不用于当前界面，但不强制删除其他外观映射。
- 离线保存本地资料时标记 `pending`；下一次连接、创建绑定码或接受绑定码时重新提交。
- 服务端返回的资料时间戳优先于本地对方资料缓存。
- 天气快照不写入通用设置；仅保留当前面板会话结果。可靠旧缓存由 Relay 负责。

## 设置界面

设置页新增“基本信息”分区：

- 标题：`基本信息`
- 说明：`设置你希望对方看到的昵称和城市`
- 昵称输入框，右侧提示 `最多 20 个字`
- 城市搜索框，使用搜索图标按钮；按回车触发同一操作
- 搜索结果最多 5 条，显示城市、地区和国家
- 当前选中结果使用近黑背景、白字和红色选中图标
- 隐私说明：`仅同步城市，不读取或上传精确定位`
- 次要命令：`取消`
- 主要命令：`保存资料`

保存行为：

- 昵称或城市不合法时在对应字段附近显示短错误，不关闭设置页。
- 保存期间禁用重复提交，按钮保持稳定尺寸。
- Relay 不可用时本地保存仍成功，显示“等待同步”；绑定前会再次同步。
- 城市搜索不会因输入文字变化自动请求，只响应明确操作。

## 双方天气面板

### 视觉规格

已确认内容面板逻辑尺寸为 `424 x 466` 像素。Tauri 独立窗口可以为阴影保留透明安全区，但内容面板本身保持该尺寸和比例。

核心视觉令牌：

- 背景：`#fffefa`
- 主文字和主按钮：`#171717`
- 红色强调：`#d52820`
- 分隔线：`#dad6cf`
- 关怀提示背景：`#f2f0eb`
- 外边框：1px 近黑色
- 圆角：7px；内部按钮不超过 5px
- 字距：0
- 面板标题：21px
- 当前温度：30px，使用稳定的无衬线数字字体
- 两个天气行使用固定轨道，动态文案不能改变整体面板宽高

内容层级：

1. 红色眉题：`两座城 · 一份牵挂`
2. 标题：`今天也在同一片天空下`
3. 双方城市摘要
4. `我` 的天气行
5. `TA` 的天气行
6. 规则生成的关怀提示
7. 更新时间和 `WeatherAPI.com` 署名

每个天气行显示：

- `我` 或 `TA`
- 城市名
- 本地天气图标
- 当前温度
- 天气描述
- 今日最高/最低温
- 降雨概率

天气图标使用本地线性图标，并按 `WeatherConditionV1` 映射为晴、晴间多云、多云、雾、雨、雪、雷暴和其他八类。不得使用 emoji、Unicode 字符、供应商远程图片或纯色方块代替。

### 关怀文案规则

文案只基于 `TA` 的结果，按以下优先级选择一条：

1. 降雨概率大于等于 50%：`TA 那边可能会下雨，今天记得提醒 TA 带伞。`
2. 当前温度大于等于 30°C：`TA 那边有点热，记得提醒 TA 多喝水。`
3. 当前温度小于等于 10°C：`TA 那边有点凉，记得让 TA 多穿一点。`
4. 其他情况：`今天也在同一片天空下。`

对方天气不可用时不生成错误推断，改为中性文案：`等天气更新好，再一起看看 TA 那边。`

## 菜单入口与资源

- 六宫格保持恰好 6 个入口。
- 第一个“撒娇卖萌”替换为“双方天气”。
- 其他五个入口和功能不改变。
- 新增透明背景的本地天气按钮 PNG，尺寸、留白、线条粗细和黑白红配色与现有 `new-tea-*` 按钮资源一致。
- 图标主题使用云朵、太阳和两地关联元素，不显示文字，不使用黄色方块。
- 资源必须为项目自制或明确宽松授权，并在资源说明中记录来源。

## 面板状态

### 加载

- 打开后立即显示固定尺寸面板。
- 两个天气行显示同尺寸骨架内容，标题、关闭按钮和页脚位置不移动。
- 加载状态不能暴露供应商名称以外的技术错误。

### 未绑定

- 显示：`还没有可以一起看天气的 TA`
- 提供进入绑定设置的明确按钮。
- 不调用 `/pairs/weather`。

### 资料缺失

- 自己资料缺失：提供进入基本信息设置的按钮。
- 对方城市缺失：保留对方行并显示 `等待 TA 设置城市`。
- 一方资料缺失不阻止另一方天气展示。

### 部分失败

- 成功的一方正常显示。
- 失败的一方在原行内显示 `天气暂时不可用`，不弹出第二个错误对话框。
- 失败行保留人物和城市信息。

### 旧缓存

- 正常展示天气数据。
- 更新时间旁显示 `天气暂时没有更新`。
- 不使用红色警告大块抢占情侣化主内容。

### 完全失败

- 面板保持可关闭。
- 显示短提示 `天气暂时走神了，晚点再一起看看。`
- 不自动重试，不产生付费回退；用户关闭后再次打开即可重新触发业务查询。

## 透明窗口与输入行为

- 天气面板复用现有 composer 独立窗口生命周期，关闭后恢复桌宠窗口几何。
- 内容面板以外的 WebView 区域必须透明，不能出现白色或黑色矩形背景。
- 只有面板、关闭按钮和可见命令进入交互区域；透明区域继续点击穿透。
- 打开天气面板不能修改持久化的点击穿透设置。
- 面板与消息发送、外卖发送、设置和计时器控制器互斥，不允许多个独立面板重叠。
- 边缘隐藏功能不在本任务中修改；从边缘状态打开天气时只使用既有独立面板恢复机制。

## 安全、隐私与运行约束

- 不请求定位权限，不读取 IP 位置，不上传精确位置。
- API Key 不写日志、不返回客户端、不包含在错误消息中。
- Relay 只允许已认证设备搜索城市和保存资料。
- 双方天气接口只允许活动绑定成员访问，只返回该绑定双方资料和天气。
- 资料和城市字段都进行长度、类型和数值范围校验。
- WeatherAPI 请求设置连接和响应超时；供应商响应通过适配层校验后才进入缓存。
- 搜索和天气路由设置设备及 IP 级限流，避免免费额度被轻易消耗。

## 配置与部署

Relay 配置增加：

- `WEATHER_API_KEY`：WeatherAPI 免费 Key；缺失时天气与城市搜索返回可识别的服务未配置错误。
- `WEATHER_REQUEST_TIMEOUT_MS`：可选，使用保守默认值，非法值回退默认。

部署示例文件只保留空占位和说明，不提交真实 Key。Relay `/health` 保持不泄露配置内容；可以返回布尔值 `weatherConfigured`，不得返回 Key 或 Key 片段。

README 或 Relay 部署文档应说明：注册 WeatherAPI 免费套餐、配置环境变量、免费额度耗尽后的降级行为，以及应用不包含付费回退。

## 模块边界

- `shared`：资料、天气、HTTP 和 WebSocket 协议类型与解析校验。
- `server/repository`：资料持久化、绑定资料读取和鉴权。
- `server/weather`：WeatherAPI 客户端、标准化映射、缓存、请求合并和错误分类。
- `server/http`：资料、城市搜索和双方天气路由。
- `server/websocket`：`peer.profile` 能力协商与推送。
- `settings`：本地资料、设置表单和待同步状态。
- `sync`：资料 HTTP 客户端、绑定响应投影和 WebSocket 对方资料事件。
- `weather`：面板状态、展示模型、关怀文案和天气图标映射。
- `interaction`：菜单入口和图标资源映射。
- `app`：只负责组合这些边界和控制独立面板生命周期，不实现供应商解析或资料校验细节。

## 测试策略

### 共享协议

- 合法和非法资料解析。
- 城市字段长度与坐标范围。
- 新旧绑定响应兼容。
- `peer.profile` 解析和未知能力兼容。
- 天气响应的完整、部分失败和旧缓存分支。

### Relay

- 数据库迁移在新库和旧库上可重复执行。
- 资料保存、鉴权、读取和绑定对象资料返回。
- 绑定完成时双方收到正确对方资料。
- 在线资料更新触发一次 `peer.profile`，离线后重连获得最新资料。
- 城市搜索规范化、24 小时缓存、限流和供应商错误映射。
- 天气缓存命中、1 小时过期、6 小时旧缓存、超过 6 小时拒绝展示。
- 同键并发请求合并。
- 两地独立成功和失败。
- API Key 缺失、超时、额度耗尽和无效响应。
- 测试使用伪时钟和伪供应商，不依赖真实网络或真实 Key。

### 客户端

- 基本资料字段校验、明确搜索、结果选择、保存和待同步状态。
- 未完成资料阻止新绑定。
- 绑定响应和 `peer.profile` 更新本地对方资料。
- 六宫格入口数量不变，“双方天气”替换正确。
- 天气面板加载、成功、部分失败、完全失败、资料缺失、未绑定和旧缓存状态。
- 关怀文案优先级和边界温度、降雨概率。
- 固定尺寸、文本溢出和关闭恢复行为。
- 点击穿透设置不被天气面板修改。

### 视觉与桌面验收

- 在真实 Tauri debug 客户端中截取天气面板和基本信息设置。
- 与批准设计稿逐项比较尺寸、字体、颜色、边框、间距、图标、文案和透明外层。
- 验证 100%、125%、150% Windows 缩放下无文本重叠和矩形背景。
- 验证两台客户端绑定、资料更新和双方天气显示。
- 验证 Relay 无 Key、供应商失败和旧缓存降级。

## 验收标准

- 设置页可保存昵称和标准城市，且服务端重启后资料仍存在。
- 首次绑定完成后双方无需重复设置即可看到对方昵称和城市。
- 绑定后修改资料，在线对方即时更新；离线对方重连后更新。
- 六宫格仍为 6 个入口，“双方天气”使用真实本地图标资源。
- 每次打开天气面板都会请求 Relay；1 小时内不重复请求天气供应商。
- 缓存过期后重新请求；失败时仅使用 6 小时内旧缓存并明确标记。
- 双方当前天气、当前温度、今日最高/最低温和降雨概率均可展示。
- 一方失败时另一方仍正常显示。
- 面板与已确认设计稿保持一致，外层透明且没有方形背景。
- 不读取精确定位，不泄露 API Key，不允许任意坐标查询。
- 免费额度耗尽时功能降级但不会产生付费请求。
- 前端、Relay 和 Rust 的测试、类型检查及构建全部通过。
- 真实 Tauri 客户端视觉验收通过后重新产出 debug EXE。
